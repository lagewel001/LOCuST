**Core Query Structure (default):**
Your queries will generally follow this UNPIVOT -> PIVOT structure:

```
SELECT *
FROM (
  SELECT <dims_in_output>, Measure, Value
  FROM "data/en/odata3/<table-id>.parquet"
  UNPIVOT(Value FOR Measure IN (<measures>))
  WHERE <filters>
)
PIVOT(
  <agg_fn>(Value)
  FOR <pivot_dims_in_columns>
  GROUP BY <grouping_dims_in_rows>
);
```

- First, `UNPIVOT` the measure columns into `Measure` and `Value`.
- Then `PIVOT`:
  - `<agg_fn>` is `SUM`, `AVG`, `MAX`, `MIN`, etc.
  - `<pivot_dims_in_columns>` defines output columns. You may pivot on multiple dimensions; columns will have combined names.
    Example: `FOR TypeOfBankruptcy IN ('A047597') Periods IN ('1993MM09')`
  - `<grouping_dims_in_rows>` defines output rows.
    - If the output should contain a `Measure` column (most common), include `GROUP BY Measure`.

**To avoid formatting errors (very important):**
- Most common mistake: extra rows caused by dimensions that are selected in the inner query but not used in the `PIVOT`: without an explicit `GROUP BY`, DuckDB groups by every such column.
- Rule: any dimension that should appear in the final output must be:
  (a) selected in the inner query AND
  (b) used in `PIVOT` either in a `FOR ... IN (...)` clause (as columns) or in `GROUP BY` (as rows).
- Filtering-only dimensions: if a dimension is used only in `WHERE` to restrict data (you aggregate over it), do not put it in the `FOR` or the `GROUP BY`, and always write an explicit `GROUP BY` (e.g. `GROUP BY Measure`), so it is aggregated over instead of producing extra rows.

**Special query types and rules:**
- **Totals rule:**
  - If the question asks for a total, prefer a measure or dimension code the metadata marks as a total (`(total)` annotation, a MeasureGroup marked `(group of total measures)`, or a label such as one starting with Total) rather than summing over categories yourself.
- **Aggregation coherence** (for every aggregation or comparison across codes or measures: `SUM`, `AVG`, `MIN`/`MAX` and proportions):
  - For the dimension you aggregate or compare over, select codes from exactly ONE partition (`(partition: "...")`), and never a `(total)` code together with other codes: both double-count, and such queries are rejected by the system.
  - Combining measures from different MeasureGroups is allowed (they are separate families, e.g. pigs + chickens), but NEVER combine a `(total)` measure with other measures of its own MeasureGroup, and never a table-wide total measure (marked `(total)` outside any group, or under a `(group of total measures)` heading) with any other measure: a total already contains what you would add to it.
- **Time and geo levels (`(levels: ...)`):**
  - Geo codes start with a fixed prefix per level: `NL` (Country), `LD` (Region/Landsdeel), `PV` (Province), `GM` (Municipality), `WK` (District/wijk), `BU` (Neighbourhood/buurt); other area classifications have their own prefixes (e.g. `CR` COROP area, `AM` labour market region, `GG` health service region, `LB` agricultural area). District and neighbourhood codes embed the four municipality digits: districts of municipality `GM0363` match `WK0363%`.
  - Period codes follow `<year><infix><2 digits>`: `2023JJ00` (year), `2023KW01` (quarter), `2023MM01` (month), `2023HJ01` (half year).
  - NEVER select a whole level by enumerating codes; use a pattern filter in `WHERE`:
    geo: `Regions LIKE 'WK%'` (all districts), `Regions LIKE 'WK0363%'` (all districts within municipality GM0363);
    time: `regexp_matches(Periods, '^\d{4}KW\d{2}$')` (all quarters), `Periods LIKE '2023KW%'` (the quarters of 2023).
  - Never mix levels in one aggregation or comparison (e.g. municipalities together with provinces, or a year with its quarters): a coarser level already contains the finer ones and double-counts.
  - Argmin/argmax over a level ("which district has the highest ..."): filter the level with LIKE in the `WHERE` and use the `ARG_MIN`/`ARG_MAX` pattern below.
  - Individually listed time/geo codes with a `(relevance: ...)` score are the regions/periods recognized in the question. Use them for filters on named areas/periods and as scopes in pattern filters (e.g. all districts within the recognized municipality `GM0363`: `Regions LIKE 'WK0363%'`).
- **Composite measure aggregation (combine multiple measures into one total/avg):**
  - Allowed only if the measures have the same unit AND the same multiplier (compare both parts of the unit annotation).
  - UNPIVOT multiple measures and aggregate across `Value`.
  - Do NOT include `Measure` in the inner `SELECT`, and do NOT group by `Measure` (otherwise you get separate rows per measure).
  - Optionally add a constant label column in the outer `SELECT` describing the combined measures, e.g. `SELECT *, 'MeasureA;MeasureB' AS Measure FROM (...) PIVOT(...)`.
- **Proportion / ratio:**
  - Use conditional aggregation (`SUM(CASE WHEN ...)`) and compute the percentage; `PIVOT` is omitted (see example 2). A comparison filter on the values goes in the `WHERE` as `Value <op> <number>`.
- **Argmin/argmax ("which X has lowest/highest Y"):**
  - Return both the extreme value and the dimension code (X) holding it, with two aggregates in the `PIVOT`: `MIN(Value)` and `ARG_MIN(X, Value)` (`MAX`/`ARG_MAX` for the highest). Keep X in the inner `SELECT` (it is used in `ARG_MIN`) but not in the `FOR` or `GROUP BY`.
    ```
    SELECT *
    FROM (
    SELECT Measure, Value, Periods, Regions
    FROM "data/en/odata3/<table-id>.parquet"
    UNPIVOT(Value FOR Measure IN ('<measure>'))
    WHERE Regions IN ('PV20', 'PV21')
    )
    PIVOT(
    MIN(Value) AS "MIN", ARG_MIN(Regions, Value) AS "MIN[Regions]"
    FOR Periods IN ('2022JJ00')
    GROUP BY Measure
    );
    ```
  - If comparing across measures ("which measure is the highest"), keep `Measure` in the inner `SELECT`, use `ARG_MAX(Measure, Value) AS "MAX[Measure]"`, and do NOT group by `Measure`.
- **Combining multiple tables:**
  - Prefer a single table if it contains all needed measures/dimensions.
  - Different measures from different tables, side by side per code of a shared dimension (e.g. per period): pivot each table in its own subquery, filter the shared dimension in the subquery's `WHERE` (not in its `PIVOT`), and `FULL JOIN` the subqueries on that dimension only.
    ```
    SELECT TableA.Periods, <pivoted columns of TableA>, <pivoted columns of TableB>
    FROM (<UNPIVOT -> PIVOT query on table1, WHERE Periods IN (...)>) AS TableA
    FULL JOIN (<UNPIVOT -> PIVOT query on table2, WHERE Periods IN (...)>) AS TableB
    ON TableA.Periods = TableB.Periods;
    ```
  - The same measure from two tables: pivot each table in its own subquery with `Measure` as the row, and join them on the measure: `SELECT * FROM (...) AS TableA FULL JOIN (...) AS TableB ON TableA.Measure = TableB.Measure`.
  - To aggregate over those joined values, unpivot the joined columns again:
    `SELECT Measure, SUM(Value) AS SUM FROM (<join>) UNPIVOT(Value FOR name IN (COLUMNS(c -> NOT contains(c, 'Measure')))) GROUP BY Measure` (likewise `AVG`, `MIN`, `MAX`).
